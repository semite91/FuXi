FuXi - Phase 4 - Push Notifications
Test scenarios, shredded to atomic processes.
Created: 2026-11-12 22:06 UTC
Status: CONFIRMED BY THE LEARNER ON 2026-11-12, with the defaults proposed by Claude
Amended on 2026-11-13 at the Learner's request: the 10 code review fixes (R1 to R10) changed F6, I4, I7, I8 and I10
and added C10, C11, E8, E9, F11, F12, G5, I13, I14 and B11.

Every scenario has one purpose. "Given / When / Then" is used.
Phase 4 adds the VAPID key generation, the Quartz.NET timed task that sends push notifications,
the push and notification click handling of the service worker and the push subscription flow of the Settings page.
It contains no RAG engine.

Decisions taken by the Learner on 2026-11-12:
- The push library is Lib.Net.Http.WebPush. It replaced WebPush (web-push-csharp) on 2026-11-12, because WebPush only supports the old aesgcm encoding
  and the Learner wants every browser. No better-starred .NET library supports aes128gcm. project.md is updated.
- VAPID keys are generated once by the setup script through a backend command and written to .env.
- A notification click focuses an open FuXi tab and moves it to /flashcard; a new window opens only when no tab is open.
- The first run of the timed task comes one Notification Period after startup or after a restart.

Marks:
[BE]  backend scenario, verified by an xUnit test against the PostgreSQL test database, with a fake clock.
[NOW] backend scenario, verified by an xUnit test that needs no database.
[FE]  frontend scenario, verified by a Vitest test. No test calls a real API or a real push service.
[RV]  verified by reading the code or by running a command.

==================================================

B3. [NOW] Given the generated private key, when it is decoded, then it is 32 bytes.

==================================================

E3. [BE] Given Due Words "apple" and "river", when the payload is built, then title is "apple, river".

E6. [BE] Given a sent notification that the Learner ignores, when the job runs again, then the same Words are sent again.

E8. [BE] Given more Due Words than fit in 3993 bytes, when the payload is built, then it holds the first Words that fit, its JSON is at most 3993 bytes, and title and wordIds list the same Words. (R4)
E9. [BE] Given Words left out of a full payload, when the next run comes, then they are still Due. (R4)

F. SENDING
==================================================
F1. [BE] Given no PushSubscription, when the job has words to send, then no push is sent and nothing fails.
F2. [BE] Given two PushSubscriptions, when the job runs, then the push client is called once for each endpoint.
F3. [BE] Given a send, when it is made, then the subscription's Endpoint, P256dh and Auth and the VAPID public key, private key and subject from the configuration are used.
F4. [BE] Given an endpoint that answers 410 Gone or 404 Not Found, when the job runs, then that PushSubscription is deleted. (R2)
F5. [BE] Given one endpoint that answers 410 and one that answers 201, when the job runs, then only the 410 entry is deleted and the other one still receives the push.
F6. [BE] Given an endpoint that answers another error (not 410 or 404), when the job runs, then the error is logged, the entry is kept and the other endpoints still receive the push.
F7. [NOW] Given empty VAPID keys, when the job runs, then no push is sent and a warning is logged.
F8. [NOW] Given the push client, when it is read, then it is behind an interface, so tests use a fake client and no real push service is called.
F9. [NOW] Given a subscription endpoint whose host is not in PushHosts, when the job runs, then it is not called (SSRF protection).
F10. [NOW] Given the push client, when it is read, then its HttpClient comes from IHttpClientFactory with a timeout.
F11. [BE] Given two subscriptions, when a run sends, then the VAPID authentication is built once. (R10)
F12. [BE] Given a slow endpoint, when a run sends, then the other endpoint is not waited for. (R10)

==================================================
I1. [FE] Given the Settings page, when it opens, then the browser is not asked for permission and no push API is called.
I2. [FE] Given "Enable notifications", when it is clicked, then the browser asks for notification permission.
I3. [FE] Given permission "denied", when the answer comes, then GetVapidPublicKey is not called and "Notifications: blocked" is shown.
