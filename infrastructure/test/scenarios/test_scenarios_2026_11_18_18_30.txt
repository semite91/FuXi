FuXi - Phase 6e - Spotify (Spotify button, sign-in, playlist link, refresh token in the Settings table)
Test scenarios, shredded to atomic processes.
Created: 2026-11-18 18:30 UTC
Status: CONFIRMED BY THE LEARNER (2026-11-18)

Every scenario has one purpose. "Given / When / Then" is used.
Phase 6e is the last part of Phase 6 (ToDos_review.txt #54 to #58). It replaces the Phase 5d design (PR #21, issue #20:
liked songs, a helper script and a token file) with one Spotify playlist the Learner chooses on the Settings page, the
same way as Google Drive in 6c. PR #21 is closed as superseded; its resource, fixtures and tests are brought over and
reworked.

Why the design changed (found 2026-11-18, Spotify's Web API changes of February 2026 for Development Mode apps):
- GET /playlists/{id}/tracks is renamed GET /playlists/{id}/items.
- Playlist items are returned only for playlists the signed-in user owns or collaborates on; for any other playlist
  Spotify gives the metadata without the items.
- A token from the Client ID and Secret alone has no user. It is expected to be unable to read the items, so the read
  uses the Learner's own refresh token (Authorization Code flow). This is not stated in the docs; the live check (I3)
  confirms the read works, and the field names of the recorded answers are checked against the docs when the code is built.
- The Learner chose option A (Spotify sign-in) on 2026-11-18. ToDos_review #56's "only the Client ID and Secret" and
  "only public playlists" no longer hold; the Learner's own playlists (public or private) are read.

Decisions taken by the Learner (2026-11-18):
- The sign-in belongs to the API like Notion and Google Drive; the refresh token and the playlist link are kept in the
  Settings table; the engine's connection stays read-only (same as 6c Q2).
- The playlist link is saved through the pop-up of 6c (LinkDialog), reused.
- The Spotify Developer Client ID and Secret are asked from the Learner when the live check starts (#57).

Proposed by Claude, to confirm with these scenarios:
- The endpoints follow ApiRoutes: GET /api/SpotifyConnect, GET /api/SpotifyCallback, GET /api/GetSpotifyConnection and
  POST /api/UpdateSpotifyPlaylist.
- The .env keys are SPOTIFY_CLIENT_ID, SPOTIFY_CLIENT_SECRET and SPOTIFY_REDIRECT_URI (FUXI_APP_URL is shared). They
  replace RAG_SPOTIFY_CLIENT_ID, RAG_SPOTIFY_CLIENT_SECRET and RAG_SPOTIFY_TOKEN_FILE of PR #21 (never merged).
  SPOTIFY_REDIRECT_URI is http://127.0.0.1:5000/api/SpotifyCallback until the hosting is decided (#21); Spotify allows
  http only for a loopback address, written as 127.0.0.1, not localhost.
- The sign-in goes to https://accounts.spotify.com/authorize with response_type=code, the scopes playlist-read-private
  and playlist-read-collaborative, and a state. The code is exchanged at https://accounts.spotify.com/api/token with a
  Basic Authorization header (client ID and secret).
- The Settings table holds three Spotify rows: SpotifyRefreshToken, SpotifyName (the display name from GET /v1/me) and
  SpotifyPlaylistId. The access token of the sign-in is used once for the /v1/me call and is not saved.
- When a sign-in connects a different Spotify account than the saved one (by user id), the saved playlist is cleared.
  SpotifyUserId is therefore a fourth row.
- The engine gets an access token from the refresh token at each build (grant_type=refresh_token, Basic header), keeps
  it in memory only, and ignores a new refresh token Spotify may return (the old one stays valid; the connection is
  read-only). It reads GET /v1/playlists/{id}/items with limit=50 and follows Spotify's next link while it starts with
  https://api.spotify.com/v1/playlists/{id}/items.
- The song document and metadata are those of PR #21 (Song / Musician / Album / Link; name, path empty, musician, album,
  type "song"); the timestamp is the time the song was added to the playlist. Skips and the same-track-once rule stay.
- Connected without a saved playlist: Spotify is skipped and the build is still complete (as Google Drive, 6c Q6).
- The row: "Connected: <name>"; with a playlist, "Playlist chosen" and a link that opens it in a new tab.
- Clicking the Spotify button: not connected, it starts the sign-in; connected, it opens the pop-up. When connected, a
  second small button "Connect again" starts the sign-in (for a refused token).
- Item 58: the RAG workflow (pipeline, engine, prompts) does not change; only the resource's source changes.

==================================================
A. SIGN-IN START (GET /api/SpotifyConnect)
==================================================
A1. [BE] Given SPOTIFY_CLIENT_ID and SPOTIFY_REDIRECT_URI, when /api/SpotifyConnect is called, then it answers 302 to https://accounts.spotify.com/authorize with client_id, response_type=code, redirect_uri, scope=playlist-read-private playlist-read-collaborative and state.
A2. [BE] Given two calls, when their redirect addresses are read, then each has its own random state value.
A3. [BE] Given a state made by /api/SpotifyConnect, when its callback comes within 10 minutes, then it is accepted; after 10 minutes (fake clock) it is refused.
A4. [BE] Given a state made by Notion or Google Drive, when it comes back to /api/SpotifyCallback, then it is refused, and the other way round.
A5. [BE] Given SPOTIFY_CLIENT_ID, SPOTIFY_CLIENT_SECRET or SPOTIFY_REDIRECT_URI is empty, when the API starts, then one error naming only the empty keys is logged and the API still starts; /api/SpotifyConnect then redirects to <FUXI_APP_URL>/settings?spotify=failed. Notion and Google Drive keep working.

==================================================
B. SIGN-IN CALLBACK (GET /api/SpotifyCallback)
==================================================
B1. [BE] Given a callback with a code and a known state, when it is handled, then the code is sent to https://accounts.spotify.com/api/token as a form with grant_type=authorization_code, code and redirect_uri, with the Basic Authorization header.
B2. [BE] Given Spotify answers with access_token, refresh_token and a scope that holds playlist-read-private and playlist-read-collaborative, when the callback goes on, then it calls https://api.spotify.com/v1/me with that access token.
B3. [BE] Given /v1/me answers an id and a display name, when the callback ends, then the Settings table has SpotifyRefreshToken, SpotifyUserId and SpotifyName with these values, written in one SaveChanges, and it answers 302 to <FUXI_APP_URL>/settings?spotify=connected.
B4. [BE] Given /v1/me has no display name, when the callback ends, then SpotifyName is the user id.
B5. [BE] Given the rows already exist, when a new sign-in with the same user id succeeds, then the rows are updated in place and SpotifyPlaylistId is kept.
B6. [BE] Given a saved SpotifyPlaylistId and a new sign-in with a different user id, when the callback ends, then SpotifyPlaylistId is emptied in the same SaveChanges.
B7. [BE] Given a callback whose state is unknown, expired, missing or already used, when it is handled, then no call is sent to Spotify, no Settings row changes, and it answers 302 to ?spotify=failed.
B8. [BE] Given a callback with error=access_denied, also with a code, when it is handled, then no call is sent, no row changes, and it answers ?spotify=failed.
B9. [BE] Given Spotify answers the exchange with an error status, without access_token, without refresh_token, or with a scope that lacks a playlist scope, when the callback ends, then no row changes and it answers ?spotify=failed.
B10. [BE] Given the /v1/me call fails (error status, timeout, unreadable answer), when the callback ends, then no row changes and it answers ?spotify=failed.
B11. [BE] Given any failure in B9 or B10, when it is logged, then the log names only the status or error type, never the code, a token or the client secret.

==================================================
C. CONNECTION STATE AND PLAYLIST (GET /api/GetSpotifyConnection, POST /api/UpdateSpotifyPlaylist)
==================================================
C1. [BE] Given no SpotifyRefreshToken row, or an empty one, when /api/GetSpotifyConnection is called, then it answers { isConnected: false, name: null, playlistId: null }.
C2. [BE] Given a refresh token, a name and a playlist ID, when it is called, then it answers { isConnected: true, name: <name>, playlistId: <id> }; an empty name or playlist answers null for it.
C3. [BE] Given any Settings rows, when the answer is read, then it holds no refresh token and no user id.
C4. [BE] Given a connected Spotify, when /api/UpdateSpotifyPlaylist gets { playlistLink: "https://open.spotify.com/playlist/<id>" } (also with ?si=..., or an /intl-xx/ part), then SpotifyPlaylistId is saved as <id> and it answers 200 with { playlistId: <id> }.
C5. [BE] Given the forms spotify:playlist:<id> and a bare ID (22 letters and digits), when they are saved, then SpotifyPlaylistId is <id>.
C6. [BE] Given an empty text, an album, track or artist link, another site's link or an ID of another form, when it is saved, then it answers 400 with "This is not a Spotify playlist link." and no row changes.
C7. [BE] Given Spotify is not connected, when /api/UpdateSpotifyPlaylist is called, then it answers 409 and no row changes.
C8. [BE] Given a saved playlist, when another valid link is saved, then the row is updated in place.

==================================================
D. RAG ENGINE READS THE PLAYLIST WITH A FRESH TOKEN
==================================================
D1. [PY] Given SpotifyRefreshToken and SpotifyPlaylistId rows, when a build reads Spotify, then the engine posts grant_type=refresh_token with the refresh token to https://accounts.spotify.com/api/token with the Basic header (SPOTIFY_CLIENT_ID, SPOTIFY_CLIENT_SECRET) before any playlist call.
D2. [PY] Given the access token, when a playlist call is sent, then it carries "Authorization: Bearer <token>" and the token is not in the URL.
D3. [PY] Given the engine, when it gets an access token, or Spotify answers with a new refresh token, then both stay in memory and nothing is written to the Settings table.
D4. [PY] Given no refresh token row, or an empty one, when a build runs, then Spotify is skipped with "resource spotify: not connected, skipped" and the other sources build.
D5. [PY] Given a refresh token but no playlist, when a build runs, then Spotify is skipped with "resource spotify: no playlist chosen, skipped".
D6. [PY] Given Spotify is skipped and every other source succeeds, when the build ends, then the build is complete.
D7. [PY] Given the token endpoint answers 400 invalid_grant, when a build reads Spotify, then Spotify fails with "Spotify token rejected: connect Spotify again on the Settings page", the build is not complete and the old collections are kept. Given 400 or 401 invalid_client, the error says to check SPOTIFY_CLIENT_ID and SPOTIFY_CLIENT_SECRET. Another refusal names only the status and error.
D8. [PY] Given a playlist call answers 401, when a build reads Spotify, then it fails like D7.
D9. [PY] Given SPOTIFY_CLIENT_ID or SPOTIFY_CLIENT_SECRET is empty while a refresh token is saved, when a build reads Spotify, then Spotify fails naming only the empty key.
D10. [PY] Given the playlist answers 403 or 404 (wrong ID, or a playlist of another account), when a build reads Spotify, then Spotify fails with "Spotify playlist not found: choose the playlist again on the Settings page".
D11. [PY] Given the database cannot be reached, when a build reads the Spotify rows, then Spotify fails (it is not skipped) and the error names only the error type.
D12. [PY] Given a refresh call that times out, drops its connection or gets a 5xx answer, when the resource reads, then it is not tried again (Spotify may have used the token) and the source fails; a 429 is waited for and tried again.
D13. [PY] Given any failure of the sign-in, when its error is logged, then it holds no access token, no refresh token and no client secret.

==================================================
E. PLAYLIST SONGS READ
==================================================
E1. [PY] Given recorded answers over 3 pages, when the resource reads, then /v1/playlists/<id>/items is called first with limit=50, each page's next link is followed, and every song is read once.
E2. [PY] Given a last page without a next page, when it is read, then no further page is asked.
E3. [PY] Given a next link that does not start with the playlist's items address, a next link already followed, or one whose offset does not move forward, when it is read, then the Spotify resource fails with an error that holds the endpoint and not the link.
E4. [PY] Given an empty playlist, when the resource reads, then it gives no document and no error.
E5. [PY] Given an item without a track, a podcast episode, a local file or a song without a name, when it is read, then it is skipped, the others are read and the skip is counted.
E6. [PY] Given the same track id in two items, when they are read, then one document is made and the second is counted as repeated.
E7. [PY] Given a 429 answer with Retry-After, when the resource reads, then it waits as Retry-After says and tries again.
E8. [PY] Given a 5xx answer, a timeout or a dropped connection on a playlist call, when the resource reads, then it waits 1, 2, 4 and 8 seconds and tries again, at most 5 attempts, then fails the source.
E9. [PY] Given a 200 answer that is not a JSON object, or a page whose items are missing, null or not a list, when it is read, then the Spotify resource fails with an error that holds the endpoint; only an empty item list with no next page ends the read.
E10. [PY] Given a failure, when the error is raised, then it holds the status or error kind and the endpoint, not a token and not a song's name.
E11. [PY] Given a read, when it ends or fails, then its summary holds the songs, skipped items, repeated items, calls, rate limit waits, network retries and seconds.
E12. [PY] Given the resource class, when it is read, then it implements the Resource base with kind TEXT, uses the shared http_retry helpers and the shared settings_store reads, and the other resources' tests pass unchanged.

==================================================
F. SONG DOCUMENT
==================================================
F1. [PY] Given a recorded song, when the document is built, then its text has the Song, Musician, Album and Link lines.
F2. [PY] Given a song with 3 artists, when the document is built, then the Musician line and the musician metadata hold the 3 names joined with ", ".
F3. [PY] Given a song without an album name, when the document is built, then the Album line is left out and the document is still made.
F4. [PY] Given a link that does not start with https://open.spotify.com/, when the document is built, then the Link line is left out.
F5. [PY] Given a song, when its metadata is built, then it has name, path (empty text), musician, album, type "song" and timestamp (the time it was added to the playlist), and every value is a string.
