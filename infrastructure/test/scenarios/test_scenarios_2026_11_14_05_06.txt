Every scenario has one purpose. "Given / When / Then" is used.
Phase 5b adds the second source, Google Drive, to the RAG engine built in 5a. The Learner's images are embedded with
CLIP into fuxi_image, and the photo method may show one of the Learner's own images on the card.
Letterboxd + TMDB (5c) and Spotify (5d) come later. Evaluation (ragas) is version 2.

Decisions taken by the Learner on 2026-11-14 (grilling rounds 1 to 3):
- The engine signs in to Drive with a Google Cloud service account. RAG_GOOGLE_SERVICE_ACCOUNT_FILE in the root .env
  holds the path of its JSON key; the key is kept in the git-ignored rag/secrets/ folder.
- Every image the service account can see is read, subfolders included. The Learner shares a folder with the
  service account's email to add images; there is no folder setting.
- Each image is downloaded as Drive's 512 px thumbnail; the full file is used only when Drive has no thumbnail.
  Pillow opens it. HEIC photos are included through their Drive thumbnail. A file Pillow cannot open is skipped and
  counted in the embedding log.
- google-auth signs in with the service account; the installed httpx calls the Drive REST API. google-auth is the
  only new direct library and is vetted before installation.
- For the photo method, the Drive images above RAG_IMAGE_THRESHOLD are sent to Gemini by name and path. Gemini picks
  one of them or falls back to a web image found by Google Search.
- A chosen Drive image is stored in the photo content as a JPEG data: URL of at most 512 px. The card shows a
  data:image/jpeg image as well as an https image.

Proposed by Claude, to confirm with these scenarios:
- An image document's text is the Base64 of its 512 px JPEG. Metadata: name (file name), path (parent folder names
  joined with " / "), type "picture" and timestamp (the photo's taken time when Drive has it, otherwise its created time).
- The pipeline decodes the Base64 into a picture before CLIP embeds it (review item 6 of Phase 5a).
- Each Drive image goes to Gemini as {"image_url": "drive:<n>", "name", "path"}, <n> being its place in the image
  results. Gemini answers image_url "drive:<n>"; the code puts that image's data: URL in the content. The prompt
  files are not changed.
- Drive calls follow Notion's retry rules: a 429 or a 5xx answer, a dropped connection or a timeout is tried again
  after 1, 2, 4 and 8 seconds, at most 5 attempts. Each read writes its summary to the embedding log.
- A parent folder the service account cannot see (403 or 404) ends the image's path; the image is still read.
- A missing RAG_GOOGLE_SERVICE_ACCOUNT_FILE, a missing key file or a refused sign-in makes the Drive source fail, so
  the build is not complete and the old collections are kept, as with Notion.
- Live tests use the real service account only when RAG_LIVE_TESTS=true in .env.test.

Marks:
[PY]  Python scenario, verified by a pytest test with a fake embedder and recorded Drive and Gemini answers.
[LIVE] Python scenario, verified by a pytest test that loads the real models or calls a real API; runs only when enabled.
[FE]  frontend scenario, verified by a Vitest test.
[RV]  verified by reading the code, running a command or a real run.

==================================================
C. GOOGLE DRIVE RESOURCE
==================================================
C1. [PY] Given a service account key file, when the resource signs in, then google-auth makes a token with the drive.readonly scope only.
C2. [PY] Given a key file that does not exist, when the resource reads, then it fails and the error names RAG_GOOGLE_SERVICE_ACCOUNT_FILE without the key's content.
C3. [PY] Given recorded files.list answers over 2 result pages, when the resource reads, then every image file is read once.
C4. [PY] Given files.list, when it is called, then it asks only for image files that are not in the trash.
C5. [PY] Given an image with a thumbnailLink, when it is downloaded, then the 512 px thumbnail is fetched with the access token.
C6. [PY] Given an image without a thumbnailLink, when it is downloaded, then the full file is fetched (alt=media).
C7. [PY] Given a downloaded image larger than 512 px, when it is prepared, then it is scaled so its longest side is 512 px, keeping its shape.
C8. [PY] Given a downloaded PNG with transparency, when it is prepared, then it becomes an RGB JPEG.
C9. [PY] Given a downloaded file Pillow cannot open, when it is prepared, then it is skipped, the others are still read and the skip is counted in the read summary.
C10. [PY] Given an image, when its document is built, then the text is the Base64 of its JPEG and metadata has name, path, type "picture" and timestamp.
C11. [PY] Given an image with a taken time in its photo data, when its timestamp is set, then the taken time is used; without it, the created time is used.
C12. [PY] Given an image in nested folders, when its path is built, then the folder names are joined with " / ", from the top folder down.
C13. [PY] Given 2 images in the same folder, when their paths are built, then the folder is asked from Drive once.
C14. [PY] Given a parent folder that answers 403 or 404, when the path is built, then the path stops there and the image is still read.
C15. [PY] Given a parent folder that answers 500 after every attempt, or 401, when the path is built, then the Drive resource fails.
C16. [PY] Given a Drive answer 429, or a 403 with reason rateLimitExceeded or userRateLimitExceeded, when the resource reads, then it waits and tries again.
C17. [PY] Given a dropped connection or a timeout, when the resource reads, then it waits 1, 2, 4 and 8 seconds and tries again, at most 5 attempts.
C18. [PY] Given a Drive read, when it ends or fails, then its summary holds the images, skipped files, calls, rate limit waits, network retries and seconds.
C19. [PY] Given no image shared with the service account, when the resource reads, then it gives no document and no error.
C20. [PY] Given the new resource class, when it is added, then it implements the Resource base with kind IMAGE, and the Notion resource's behavior is not changed:
     its retry code moves to a shared module used by both resources and every Notion test still passes (open-closed, DRY).
C22. [PY] Given a 403 with any other reason on a download, when the resource reads, then the file is skipped as before, without a retry.
C23. [PY] Given 10 images, when they are downloaded in parallel (a bounded number of workers), then the documents keep the order of the file list.
C24. [PY] Given images in the same folder downloaded in parallel, when their paths are built, then the folder is asked from Drive once.
C25. [PY] Given parallel downloads, when the read ends, then the read summary counts every image, skip and retry exactly once.
C26. [PY] Given a rate-limit 403 that still fails after the last retry, on a download or a folder lookup, when the resource reads, then the Drive resource fails
     (no image is skipped and no path is cut because of throttling).
C27. [PY] Given an unexpected error while a file is downloaded, when the resource reads, then the resource fails; only a picture Pillow cannot open is skipped.
C28. [PY] Given a very large original without a thumbnail, when it is prepared, then a JPEG is decoded at reduced size and a decompression bomb warning makes it a counted skip.
C21. [LIVE] Given the real service account, when the resource reads, then at least one image document is returned.
